# L2 - Detailed Requirements

> Each L2 traces to one or more L1 requirements in `L1.md`. Acceptance criteria use Given/When/Then so they translate directly to tests. Every acceptance test in this repo shall carry a `Traces to: L2-NNN` header comment.

---

## L2-001: User signup creates account and family
**Traces to:** L1-001

The system shall accept a signup payload (email, password, optional family name, optional home location), create a `User` row, create an empty `Family` row owned by that user, issue an access token + refresh token, and return both with the user record.

**Acceptance Criteria:**
1. Given no user exists with email `new@example.com`, when a `POST /api/auth/register` is sent with `{email: "new@example.com", password: "Passw0rd!"}`, then the response status shall be 201 and the body shall contain a non-empty `tokens.accessToken`, a non-empty `tokens.refreshToken`, and a `user` with `emailVerifiedUtc=null`.
2. Given a user already exists with normalized email `new@example.com`, when registration is retried with the same email, then the response shall be 409 with error code `email_in_use`.
3. Given any successful registration, when the database is inspected, then exactly one new `Family` row shall exist with the new user's `FamilyId` pointing to it.
4. Given a password shorter than 8 characters, when registration is attempted, then the response shall be 400 with a validation error naming the password field.
5. Given the signup form on `/create-account` with terms unchecked, when the user fills email/password, then the submit button shall remain disabled.

## L2-002: User login returns a token pair
**Traces to:** L1-001

The system shall authenticate a user by `Email` + `Password`, issue a fresh access token + refresh token on every successful login, and return a generic 401 error on any credential failure (without distinguishing "no such user" from "wrong password").

**Acceptance Criteria:**
1. Given a seeded user `quinntynebrown@gmail.com` with password `password123`, when `POST /api/auth/login` is sent with those credentials, then the response shall be 200 with `tokens.accessToken`, `tokens.refreshToken`, and `user.email` matching the seeded user.
2. Given the same user, when login is sent with a wrong password, then the response shall be 401 with error code `invalid_credentials` and the response body shall not reveal whether the email exists.
3. Given a successful login, when the database is inspected, then a new `RefreshToken` row shall exist with `ExpiresAtUtc` 14 days in the future and `RevokedAtUtc` null.
4. Given a live refresh token, when `POST /api/auth/refresh` is sent with it, then the response shall be 200 with a new access + refresh pair, the presented token shall be revoked and linked to its replacement via `ReplacedByTokenId`, and presenting it again shall return 401 `refresh_token_revoked`.

## L2-003: Sign-out revokes the active refresh token
**Traces to:** L1-001

A signed-in user shall be able to sign out via a confirmation dialog from the Family page or account menu, after which their refresh token is revoked and stored token material is cleared from the client.

**Acceptance Criteria:**
1. Given the user is signed in, when they tap "Sign out" on `/family` and confirm the dialog, then the client shall clear access and refresh tokens from both `localStorage` and `sessionStorage`, and the next protected request shall return 401.
2. Given an active refresh token at sign-out time, when the dialog is confirmed, then the client shall call `POST /api/auth/logout` with it and the corresponding `RefreshToken.RevokedAtUtc` shall be set in the database (the endpoint is anonymous and idempotent; valid requests return 204, while malformed payloads fail validation).
3. Given the sign-out dialog is open, when the user presses Escape or taps the backdrop, then the dialog shall close without signing the user out.

---

## L2-004: Forgot-password flow accepts an email
**Traces to:** L1-001

A signed-out user shall be able to request a password-reset link by entering their email. The system shall not reveal whether the email is registered.

**Acceptance Criteria:**
1. Given the user is on `/reset-password`, when they submit a syntactically valid email, then the page shall display its sent state regardless of whether the email is registered.
2. Given an unregistered email is submitted, when the response is inspected, then it shall be indistinguishable from a registered email submission (same status, same shape, same latency budget).
3. Given the email field is empty or malformed, when the user submits, then a field-level validation error shall appear inline and the form shall not be submitted.

---

## L2-005: Reset-password applies a new password via token
**Traces to:** L1-001

The system shall accept a reset token plus a new password and confirmation, validate the token, enforce password complexity, and rotate any existing refresh tokens for that user on success.

**Acceptance Criteria:**
1. Given a valid, unexpired reset token, when the user submits matching passwords meeting complexity rules, then the page shall display its done state and the user's password hash shall be updated.
2. Given an expired or invalid token, when the user submits, then an inline error shall appear with an action returning to the request state on `/reset-password`, and the password hash shall not change.
3. Given the password and confirmation fields differ, when the user submits, then a field-level "passwords do not match" error shall appear and submission shall be blocked.
4. Given a password shorter than 8 characters, or missing a number/symbol, when the user types, then an inline rule-checklist shall indicate which rules are not yet satisfied.

## L2-006: Email verification links activate the account
**Traces to:** L1-001

The system shall accept a verification token, mark the corresponding user as verified, and surface either a success or error state on `/verify-email`.

**Acceptance Criteria:**
1. Given a valid, unexpired, unconsumed verification token, when the user visits `/verify-email?token=<token>`, then `User.EmailVerifiedUtc` shall be set to the current UTC time if not already set, and the page shall show a success state with primary CTA "Set up your family".
2. Given an invalid or expired token, when the user visits the page, then an error state shall appear with a link to sign in or request a new link.
3. Given the user reaches the success state, when they tap "Skip to this weekend", then they shall be redirected to `/weekend`.

---

## L2-007: Remember-me toggle controls token persistence
**Traces to:** L1-001

The login form's "remember me" toggle shall select between durable persistence (`localStorage`) and session-only persistence (`sessionStorage`) for the access and refresh tokens.

**Acceptance Criteria:**
1. Given remember-me is checked, when the user logs in successfully and then reloads the page, then the access token shall still be present in `localStorage` and the user shall remain on a protected route.
2. Given remember-me is unchecked, when the user logs in successfully, then `localStorage` shall contain no Saturdaze token, `sessionStorage` shall contain the access token, and closing the tab shall end the session.

## L2-008: JWT-protected endpoints require a valid bearer token
**Traces to:** L1-001, L1-012

Every endpoint except `POST /api/auth/register|login|refresh|logout|forgot-password|reset-password|verify-email|resend-verification`, `GET /api/weather` (no PII), `GET /api/weekends/shared/{token}` and `GET /api/weekends/{id}/calendar.ics` (capability URLs that browsers and calendar clients fetch without a bearer) shall reject requests that lack a valid `Authorization: Bearer <jwt>` header. `GET /api/activities|/api/restaurants|/api/events` are personalized per family (votes, locks, novelty history) and therefore require a bearer too (ADR-008). Enforcement is a global fallback authorization policy; anonymous routes opt out explicitly.

**Acceptance Criteria:**
1. Given no Authorization header, when `GET /api/auth/me` is requested, then the response shall be 401.
2. Given an expired access token, when any protected endpoint is requested, then the response shall be 401.
3. Given a token signed with the wrong key, when any protected endpoint is requested, then the response shall be 401.
4. Given a valid bearer token, when `GET /api/auth/me` is requested, then the response shall be 200 with the caller's `UserDto`.

## L2-009: Family profile view returns the caller's family
**Traces to:** L1-002

`GET /api/family` shall return the authenticated caller's family with all members, commitments, and preferences in one response.

**Acceptance Criteria:**
1. Given an authenticated user whose family has 4 members and 3 commitments, when `GET /api/family` is requested, then the response shall include exactly those 4 members and 3 commitments.
2. Given an authenticated user, when `GET /api/family` is requested, then the response shall include `homeLocation`, `budgetEnabled`, members (id, name, age), commitments (id, title, dayOfWeek, startTime, endTime), and preferences (id, kind, value).
3. Given no authenticated user, when `GET /api/family` is requested, then the response shall be 401.

## L2-010: Family profile edit persists changes
**Traces to:** L1-002

`PUT /api/family` shall accept a full or partial family profile and persist additions, edits, and removals to members, commitments, and preferences.

**Acceptance Criteria:**
1. Given an existing family with members `[Quinn, Sara]`, when `PUT /api/family` is sent with members `[Quinn, Sara, Eli]`, then a subsequent `GET /api/family` shall return 3 members including Eli with the supplied age.
2. Given an existing commitment "Swim 9–10am Sat", when `PUT /api/family` is sent omitting that commitment, then it shall be removed from the family.
3. Given the profile page on `/family`, when the user taps "Add member" then a CDK dialog shall open (no inline form), and saving shall call `PUT /api/family` exactly once with the new member appended.
4. Given an invalid payload (e.g., member with negative age), when `PUT /api/family` is sent, then the response shall be 400 with a validation error.

## L2-011: Recurring commitments produce locked blocks
**Traces to:** L1-002, L1-004

Every `Commitment` on the family profile shall materialize as a locked itinerary block on every generated weekend at the commitment's day and time window.

**Acceptance Criteria:**
1. Given a family with commitment "Swim 9:00–10:00 Saturday", when a new weekend is generated, then the Saturday timeline shall contain a block titled "Swim" from 09:00 to 10:00 with `IsLocked=true` and `Kind=Commitment`.
2. Given a regenerate is requested for an existing weekend, when the response is returned, then every commitment block from the prior weekend shall remain in place at the same time.

## L2-012: Generate weekend creates a Saturday+Sunday plan
**Traces to:** L1-003

`POST /api/weekends/plan` shall create a new `Weekend` row for the requested weekend date with blocks across Saturday and Sunday, including activities, meals, drives, downtime, and any commitments from the family profile.

**Acceptance Criteria:**
1. Given an authenticated user with a family profile, when `POST /api/weekends/plan` is sent with `weekendOf=<saturday-date>`, then the response shall be 200 with a `WeekendDto` whose `weekendOf` matches the input and whose `blocks` array spans both Saturday and Sunday.
2. Given the same family generates a plan twice for the same weekend, when the database is inspected, then exactly one `Weekend` row shall exist for that family + date pair (uniqueness enforced).
3. Given no family profile data, when generation is attempted, then the response shall succeed but produce only the bare-minimum blocks the system can construct, and not throw a 500.

## L2-013: Current weekend endpoint returns the upcoming plan
**Traces to:** L1-003

`GET /api/weekends/current` shall return the family's plan for the current or next upcoming Saturday, generating one on demand if absent.

**Acceptance Criteria:**
1. Given an authenticated user with no weekends, when `GET /api/weekends/current` is requested, then a new `Weekend` for the upcoming Saturday shall be created and returned with status 200.
2. Given a weekend already exists for the upcoming Saturday, when `GET /api/weekends/current` is requested, then the response shall reference the existing weekend's ID (not create a new row).

## L2-014: Block lock toggle is idempotent
**Traces to:** L1-004

`PUT /api/blocks/{id}/lock` shall set `ItineraryBlock.IsLocked` to the request value and return the parent weekend.

**Acceptance Criteria:**
1. Given an unlocked block, when `PUT /api/blocks/{id}/lock` is sent with `{locked: true}`, then the response shall be 200 with the weekend showing that block's `isLocked=true`.
2. Given an already-locked block, when the same request is sent again, then the response shall still be 200 and the block shall remain locked (no error).
3. Given a block ID that does not exist, when the endpoint is called, then the response shall be 404.
4. Given a block that belongs to another family, when the caller is not a member of that family, then the response shall be 403 or 404 (no information leak).

---

## L2-015: Block swap replaces a slot and respects rejected suggestions
**Traces to:** L1-004

`POST /api/blocks/{id}/swap` shall replace the activity referenced by a block with the next-best candidate, optionally excluding a list of rejected activity IDs supplied by the client.

**Acceptance Criteria:**
1. Given an Activity block referencing Activity A, when `POST /api/blocks/{id}/swap` is sent with `rejectedActivityIds=[A]`, then the response shall contain that same block ID but with a different `refId` (not A).
2. Given a locked block, when swap is attempted, then the response shall be 409 with error code `block_locked` and the block shall remain unchanged.
3. Given the only remaining candidate has already been rejected, when swap is attempted, then the response shall be 200 and the block shall keep its current activity (no-op) with a `reason` annotation.

## L2-016: Regenerate preserves locks and increments RegenerateCount
**Traces to:** L1-004

`POST /api/weekends/{id}/regenerate` shall rebuild every unlocked block, leave every locked block in place, and increment `Weekend.RegenerateCount`.

**Acceptance Criteria:**
1. Given a weekend with 10 blocks of which 3 are locked, when regenerate is called, then exactly those 3 locked blocks (by ID and content) shall appear unchanged in the response, and the other 7 shall have new content.
2. Given a weekend with `RegenerateCount=2`, when regenerate is called, then the database shall show `RegenerateCount=3`.

## L2-017: Activity list applies filters and excludes age-misfits
**Traces to:** L1-005

`GET /api/activities` shall accept query filters (`indoor`, `maxDriveMinutes`, `minAge`, `maxAge`, `weather`, `tryNew`, `take`) and return activities whose attributes satisfy every supplied filter.

**Acceptance Criteria:**
1. Given seeded activities, when `GET /api/activities?indoor=true` is requested, then every item in the response shall have `indoor=true`.
2. Given seeded activities including one with `maxAge=8`, when `?minAge=9` is requested, then that activity shall not appear in the response.
3. Given `?take=3`, when the request is sent, then the response shall contain at most 3 items.
4. Given the activities page on `/ideas`, when the user taps the "Outdoor" filter chip, then only outdoor activities shall be displayed within the visible viewport without a full page reload.

The `/ideas` page shall render three labelled sections in order: weather-fit picks for the current forecast, "If the weather turns" fallbacks, and "Try something new" novelty picks.

**Acceptance Criteria:**

## L2-019: Restaurants list scopes by day and meal slot
**Traces to:** L1-006

`GET /api/restaurants` shall require a `day` and `slot` parameter, optionally narrow by `nearActivityId`, and default `wifeApprovedOnly=true`.

**Acceptance Criteria:**
1. Given a request without `day` or `slot`, when `GET /api/restaurants` is sent, then the response shall be 400 with a validation error naming the missing field.
2. Given `?day=2026-05-23&slot=Lunch&wifeApprovedOnly=true`, when the request is sent, then every item in the response shall have `wifeApproved=true` and a slot that includes lunch.
3. Given a seeded restaurant 6 minutes from a referenced activity, when `?nearActivityId=<id>` is supplied, then that restaurant shall appear earlier in the list than restaurants ≥30 min away.

## L2-020: Local events filter by weekend and drive radius
**Traces to:** L1-007

`GET /api/events` shall accept `weekendOf` and `maxDriveMinutes` (default 120). It shall return events overlapping Friday through Sunday, plus events starting within 14 days after Sunday, within the requested drive bound.

**Acceptance Criteria:**
1. Given a weekend `weekendOf=2026-05-23`, when `GET /api/events?weekendOf=2026-05-23` is sent, then every returned event shall have `startsOn` between 2026-05-22 (Fri) and 2026-05-24 (Sun) or be in a "coming soon" window of ≤14 days after.
2. Given `?maxDriveMinutes=30`, when the request is sent, then no returned event may have `driveMinutes > 30`.

## L2-021: Errand add returns updated weekend
**Traces to:** L1-008

`POST /api/weekends/{weekendId}/errands` shall append a `ShoppingErrand` to the weekend, place an `Errand` block in the best free slot (the optional `preferredDay` first, then the other day; existing downtime is reclaimed), and return the updated `WeekendDto`.

**Acceptance Criteria:**
1. Given a weekend with zero errands, when `POST /api/weekends/{id}/errands` is sent with `{description: "Costco run", estimatedMinutes: 45}`, then the response shall be 200 with `errands.length=1` and that errand's `done=false`.
2. Given the AddErrandDialog on `/weekend`, when the user submits description, minutes, and a preferred day, then exactly one POST shall be sent. On success the itinerary shall update and ErrandAddedDialog shall show the returned placement or indicate that no slot was available.

## L2-022: Errand done flag flips
**Traces to:** L1-008

`PUT /api/errands/{id}/done` shall set the errand's `Done` field to the request value.

**Acceptance Criteria:**
1. Given an errand with `done=false`, when `PUT /api/errands/{id}/done` is sent with `{done: true}`, then a subsequent `GET` of the weekend shall show that errand's `done=true`.
2. Given a non-existent errand ID, when the endpoint is called, then the response shall be 404.

## L2-023: Weather endpoint returns Sat+Sun forecast for the family's home
**Traces to:** L1-009

`GET /api/weather?weekendOf=<date>` shall return exactly two forecast entries (Saturday and Sunday) for the configured home location, with each entry exposing the date, the condition tags (`sunny`, `rain`, `snow`, `cold`, `cool`, `mild`, `warm`), high and low temperature, precipitation, and an `unavailable` flag; the client derives the day name, icon and note from those fields.

**Acceptance Criteria:**
1. Given `weekendOf=<a Saturday>`, when the endpoint is requested, then the response shall be a JSON array of length 2 with the first entry's date equal to `weekendOf` and the second entry's date equal to `weekendOf + 1 day`.
2. Given the upstream provider returns 500, when the endpoint is requested, then the response shall still be 200 with two neutral/unavailable forecast entries (no client-visible 5xx).
3. Given two requests for the same coordinates and date range within 60 minutes, when the second request fires, then it shall be served from cache (verifiable by upstream call count = 1).

**Traces to:** L1-009, L1-015

The weather provider base URL shall come from configuration (`Saturdaze:Weather:BaseUrl`), and on production startup the system shall log a warning if any production-required configuration value is unset or still holds its placeholder.

**Acceptance Criteria:**
1. Given the configuration sets `Saturdaze:Weather:BaseUrl="https://example.invalid/"`, when the API starts, then `OpenMeteoWeatherClient`'s `HttpClient.BaseAddress` shall equal that URL.
2. Given `ASPNETCORE_ENVIRONMENT=Production` and `SATURDAZE_JWT_SIGNING_KEY` is the placeholder, when the API starts, then a warning log entry shall be emitted naming the missing key.

**Traces to:** L1-010

`GET /api/weekends/history?take=N` shall return up to N past weekends ordered by `WeekendOf` descending and include each weekend's title, rating, favourite flag, and a short highlights summary.

**Acceptance Criteria:**

3. Given the saved page on `/past`, when the user taps the "Favourites" filter chip, then only `IsFavourite=true` weekends shall be displayed.

## L2-026: Weekend favourite and rating toggles persist
**Traces to:** L1-010

`PUT /api/weekends/{id}/favourite` shall set `IsFavourite` to the request value; `PUT /api/weekends/{id}/rating` (`{ rating: 1..5 | null }`) shall persist or clear a 1–5 star rating; `PUT /api/weekends/{id}/title` shall persist the user-supplied title.

**Acceptance Criteria:**

## L2-028: All pages render correctly at every breakpoint
**Traces to:** L1-011

Every routed page (`/`, `/weekend`, `/ideas`, `/ideas/food`, `/ideas/events`, `/past`, `/family`, `/review-submissions`, `/legal`, `/sample-weekend`, all auth pages) shall render usably at viewport widths 320 px, 390 px, 820 px, 1440 px, and 1920 px. (Revised 2026-09-02 with the v2 design, [ADR-009](/docs/adr/ADR-009-v2-responsive-shell.md): the v1 split view is gone; the shell is a top bar from 720 px and a bottom nav below it.)

**Acceptance Criteria:**
1. Given viewport 320×568, when any page is rendered, then no element shall overflow the horizontal viewport (no horizontal scroll).
2. Given viewport ≥720 px, when `/weekend` is rendered, then Saturday and Sunday shall sit side by side (`.grid-days` two columns) under the top bar, with each day's header sticky at the top of its column and the bottom nav absent.
3. Given viewport <720 px, when `/weekend` is rendered, then the two days shall stack into a single column, the bottom nav shall be present and clear of the device chrome (ADR-005), and each block row shall expose its details through the chevron rather than hover actions.
4. Given visual baselines captured from `docs/mocks-v2/` with `SD_BASELINE=1`, when the Playwright visual specs run, then each compared region shall match its baseline within the configured pixel-diff tolerance (the tiers and masks are [ADR-010](/docs/adr/ADR-010-visual-parity-policy.md)).

## L2-029: Passwords are stored as PBKDF2 hashes
**Traces to:** L1-012

Plaintext passwords shall never be written to the database, and the password hash format shall use PBKDF2 with at least 100,000 iterations and a per-user random salt.

**Acceptance Criteria:**
1. Given a user registers with password `Passw0rd!`, when the `Users` table is inspected, then the `PasswordHash` column shall not contain the substring `Passw0rd!`.
2. Given two users register with the same password, when their hashes are compared, then the hashes shall differ (per-user salting).

---

## L2-030: JWT signing key is loaded from environment, never committed
**Traces to:** L1-012

The JWT signing key shall be read from the `SATURDAZE_JWT_SIGNING_KEY` environment variable in production and never embedded as a real value in source control.

**Acceptance Criteria:**
1. Given `SATURDAZE_JWT_SIGNING_KEY` is unset and `ASPNETCORE_ENVIRONMENT=Production`, when the API starts, then a warning log shall indicate the signing key is using a placeholder.
2. Given the `appsettings.json` files in source control, when they are inspected, then the `Saturdaze:Jwt:SigningKey` value shall be the literal placeholder string and not a real key.

## L2-031: CORS origins are explicit allowlist in production
**Traces to:** L1-012

In production, the API shall accept cross-origin requests only from the explicit list configured in `Cors:AllowedOrigins`. Wildcard origins shall be rejected.

**Acceptance Criteria:**
1. Given `Cors:AllowedOrigins=["https://allowed.example"]` and a CORS preflight from `Origin: https://allowed.example`, when `OPTIONS /api/auth/login` is sent, then the response shall include `Access-Control-Allow-Origin: https://allowed.example`.
2. Given a preflight from `Origin: https://evil.example` and that origin is not configured, when `OPTIONS /api/auth/login` is sent, then the response shall omit `Access-Control-Allow-Origin` (or return a 403).

## L2-032: All database access uses parameterized queries
**Traces to:** L1-012

The system shall use EF Core LINQ or parameterized SQL for every database call; no string-interpolated SQL is permitted.

**Acceptance Criteria:**
1. Given the codebase, when grep is run for `FromSqlRaw`, `ExecuteSqlRaw`, or string-interpolated SQL inside C# files under `backend/src/`, then either zero matches shall exist or every match shall be wrapped with explicit parameter binding (not raw interpolation).

## L2-033: Refresh tokens rotate and track creator IP
**Traces to:** L1-012

Every issued refresh token shall record `CreatedAtUtc`, `ExpiresAtUtc` (14 days), `CreatedByIp` (when available), and on use at `POST /api/auth/refresh` shall be revoked and replaced by a new token, with the presented row\'s `ReplacedByTokenId` pointing to the replacement.

**Acceptance Criteria:**
1. Given an active refresh token, when it is exchanged at `POST /api/auth/refresh`, then the presented row shall be revoked and its `ReplacedByTokenId` shall reference the new row. Separate logins may create independent active sessions.
2. Given a refresh token reaches `ExpiresAtUtc`, when it is presented to the refresh endpoint, then the response shall be 401 and the user shall be forced to log in again.

## L2-034: API responses meet latency budgets
**Traces to:** L1-013

Read endpoints shall respond within 500 ms p95 on warm cache; write endpoints within 1000 ms p95; weekend generation within 2000 ms p95.

**Acceptance Criteria:**
1. Given a warmed API, when 50 sequential `GET /api/activities` requests are issued, then the p95 latency shall be ≤ 500 ms.
2. Given a warmed API, when 20 sequential `POST /api/weekends/plan` requests are issued for different weekends, then the p95 latency shall be ≤ 2000 ms.

## L2-035: Angular routes are lazy-loaded
**Traces to:** L1-013

Every rendered route component, including the landing page, shall be lazy-loaded via `loadComponent`, so the initial bundle excludes those pages' code.

**Acceptance Criteria:**
1. Given a production `ng build`, when the build output is inspected, then the output shall contain lazy route chunks for the current rendered pages, including `/sign-in`, `/create-account`, `/weekend`, `/ideas`, `/ideas/food`, `/ideas/events`, `/past`, and `/family`; redirect-only legacy paths shall not create page chunks.
2. Given the initial bundle, when its size is measured, then it shall respect the `500 kB warning / 1 MB error` budget configured in `angular.json`.

## L2-036: Every interactive element is keyboard reachable
**Traces to:** L1-014

Every button, link, form control, and dialog action shall be reachable via Tab order and operable with Enter/Space, and the visible focus indicator shall meet WCAG 2.1 AA contrast.

**Acceptance Criteria:**
1. Given any routed page, when a user tabs from the top of the document, then every interactive element shall receive focus in a logical order and display a visible focus ring.
2. Given an open dialog, when the user presses Tab repeatedly, then focus shall be trapped inside the dialog (not escape to the page behind it).
3. Given the user presses Escape while a dialog is open, then the dialog shall close and focus shall return to the element that triggered it.

## L2-037: Every meaningful element exposes an accessible name
**Traces to:** L1-014

Icon-only buttons shall carry `aria-label`, form fields shall have associated labels, and images carrying meaning shall have descriptive `alt` text.

**Acceptance Criteria:**
1. Given any icon-only button (e.g., back arrow, refresh, calendar in the top bar), when inspected, then it shall expose a non-empty accessible name via `aria-label` or visually hidden text.

## L2-038: Color contrast meets WCAG 2.1 AA

Non-normative. The following are verified absences in the as-built catalog, recorded here so future requirements can close them deliberately rather than by accident. They are not requirements and have no acceptance criteria:
