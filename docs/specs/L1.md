# L1 - High-Level Requirements

> Each L1 names a capability the Saturdaze system must deliver. Detailed, testable behaviors live in `L2.md`.

## L1-001: Authentication and Account Lifecycle
The system must let a family register, sign in, sign out, recover a forgotten password, reset it via emailed link, and verify ownership of their email address. Sessions must persist across page reloads when the user opts in, and must be revocable.

## L1-002: Family Profile and Preferences
Each authenticated account must own a single Family profile capturing home location, members (with ages), recurring commitments (weekly events with day/time), daily rhythm anchors, likes/dislikes, and toggleable preferences (budget, novelty, notifications). The profile must drive all downstream personalization.

## L1-003: Weekend Itinerary Generation
The system must generate a Saturday + Sunday itinerary for the family's upcoming weekend, composed of time-blocked activities, meals, drives, downtime, errands, and the family's recurring commitments. A "current weekend" must always be addressable, and any prior weekend must be retrievable by ID.

## L1-004: Itinerary Block Control
Users must be able to lock individual blocks (so regeneration leaves them alone), swap a block for a different suggestion (optionally rejecting prior suggestions), and regenerate the unlocked portion of the weekend. Locked blocks (including commitments) must never be displaced by automated regeneration.

## L1-005: Activity Discovery and Filtering
The system must present curated activities filtered by indoor/outdoor, age fit, drive time, and weather suitability, grouped to surface weather-appropriate picks first, rainy-day fallbacks second, and novelty options ("Try something new") third.

## L1-006: Restaurant Discovery and Picks
The system must surface restaurant picks for a given day and meal slot, filterable by wife-approved status, distance, and patio availability, with a featured top pick that supports voting by each family member and one-tap "lock it in" to the itinerary.

## L1-007: Local Events Discovery
The system must list local community events within driving distance of home, grouped by Saturday / Sunday / Coming-soon, and filterable by indoor/outdoor and category (Seasonal, Theatre, Festivals, etc.).

## L1-008: Errand Slot Suggestion
Users must be able to capture a shopping errand (description + estimated minutes) and have the system propose the best slot to fit it into the weekend, with the option to accept the suggestion, pick a different slot, or mark the errand done.

## L1-009: Weather Forecast for the Weekend
The system must display a daily forecast (high, low, condition, note) for Saturday and Sunday of the queried weekend, anchored to the family's home location. Forecast data must come from a reputable provider, must be cached to limit upstream load, and must degrade gracefully when the provider is unavailable.

## L1-010: Saved Weekend History
The system must persist every completed weekend, let users favourite weekends, rate them 1–5 stars, edit their title, and surface them in a history view with filters (All, Favourites, This year, 5★ only). Low-rated activities must be flagged as "avoid repeating" so future generations can skip them.

## L1-011: Responsive Web Experience
Every user-facing page must render correctly on extra-small (<576 px), small (≥576 px), medium (≥768 px), large (≥992 px), and extra-large (≥1200 px) viewports. The split-view pattern (sticky master / scrollable detail) must engage at the desktop breakpoint and collapse to single-column on mobile.

## L1-012: Security
The system must protect user credentials and session tokens, enforce authorization on all non-public endpoints, validate every external input, defend against the OWASP Top 10 (injection, broken auth, CSRF, etc.), and never log secrets or personally identifying information in plaintext.

## L1-013: Performance
API endpoints must respond within budgets appropriate to interactive use, frontend bundles must respect size budgets, weather and other slow upstream calls must be cached, and Angular route bundles must be lazy-loaded so first paint is not blocked by lower-traffic pages.

## L1-014: Accessibility
Every interactive element must be reachable and operable by keyboard, every meaningful element must expose an accessible name, color contrast must meet WCAG 2.1 AA, and dialogs must trap focus and announce themselves to assistive technology.

## L1-015: Observability and Resilience
The system must emit structured logs for every request, warn at startup when production-required configuration is missing, log upstream provider failures without crashing, and surface meaningful, non-leaky error messages to clients.

## L1-016: Deployment and Migration Pipeline
The system must deploy automatically to Azure on every push to `main`: build and publish the API to Azure App Service, apply EF Core migrations idempotently to Azure SQL, and publish the Angular frontend to Azure Static Web Apps with SPA navigation fallback.

## L1-017: Administrative CLI
A single CLI tool (`saturdaze`) must be the only supported entry point for administrative operations: applying migrations, seeding curated data (activities, restaurants, events, the Brown family, users), and resetting a development database. The CLI must accept a connection string by flag, environment variable, or configuration.

## L1-018: User-Contributed Local Events
Any authenticated user must be able to submit a local community event that isn't already in the system (e.g. a Port Credit street festival, a school fair, a one-off concert). Submissions enter a pending state and are not visible to other users until an administrator approves them. The single entry point is the primary "Suggest an event" action in the Ideas · Events header, which opens the submission dialog in place (there is no dedicated screen and no floating affordance — revised 2026-09-02 with the v2 design, see [ADR-009](../adr/ADR-009-v2-responsive-shell.md)). The submission form must capture title, date, and time as required, default the date and time to one hour from now rounded up to the next hour, and treat end time, location, description, cost, age range, and source URL as optional. A confirmation dialog summarises what was sent and the submission then appears under "Your suggestion" on the events feed until it is reviewed. Approved events appear in the regular [L1-007](#l1-007-local-events-discovery) feed indistinguishable from curated entries; rejected events are removed and the submitter is notified.

## L1-019: Design system: Design Token Foundations
The design-system product (`design-system/`) must define the complete Saturdaze visual vocabulary as `--sd-*` CSS custom properties — color, typography, spacing, radius, elevation, motion, layout, and breakpoints — in a single authoritative stylesheet that every component and documentation page consumes. No other file in the product may redeclare the token vocabulary.

## L1-020: Design system: Native Component Library
The design system must ship 29 dependency-free native Custom Elements with `sd-*` selectors and open shadow roots, organized into seven categories (actions, forms, surfaces, navigation, planning, discovery, overlays), self-registering through a single central registry module. Elements with real interaction semantics (the modal dialog) must implement complete keyboard and focus behavior themselves.

## L1-021: Design system: Component Contract Manifest
A versioned JSON manifest (`component-manifest.json`) must be the machine-readable public contract for the entire catalog: every component's attributes, slots, events, and examples, every dialog family and scenario, and every product-pattern family and responsive state. The manifest must be kept in mechanically verified parity with the component source code and registry.

## L1-022: Design system: Documentation Shell and Navigation
The catalog must be a client-side-routed single-page documentation app with deep-linkable URLs that survive browser refresh, a home page summarizing catalog coverage, an in-app not-found page, section-aware sidebar navigation, and a keyboard-operable mobile navigation drawer.

## L1-023: Design system: Foundations Documentation
The catalog must document the design tokens on a foundations page whose specimens render from the live stylesheet — color swatches, the type scale, spacing measured from computed styles, shape and elevation, motion and breakpoints, and the complete icon set — so the documentation cannot drift from the token source.

## L1-024: Design system: Component Reference and Playground
Every component must have a three-tab reference page: an overview with usage, composition, accessibility, and responsive guidance plus a contract summary; an API tab tabulating attributes, slots, and events from the manifest; and an examples tab with a live playground that mutates a real element instance, code panels that stay in sync with playground edits and support copy-to-clipboard, and an auto-generated variant matrix covering every enumerated and boolean option.

## L1-025: Design system: Dialog Catalog
The catalog must render every dialog family and every scenario inline as a static specimen — no scenario represented by a text-only placeholder — and must let users launch any scenario as a live working modal that traps focus, closes from keyboard and backdrop, and restores focus to its opener.

## L1-026: Design system: Product Pattern Catalog
The catalog must render every product-pattern family and every declared responsive state as a complete screen inside an isolated iframe, with per-specimen viewport controls that resize the frame so real media queries fire, and a dedicated chrome-free preview document addressable by query string.

## L1-027: Design system: Global Catalog Search
The catalog must provide a keyboard-driven global search across foundations, components, dialogs, and patterns, with typed results capped at a fixed count, an explicit empty state, and result activation that navigates client-side.

## L1-028: Design system: Catalog Accessibility
The documentation app must be operable by keyboard alone: skip link, programmatic focus on route change, visible focus indicators, landmark and state semantics (`aria-current`, `aria-selected`, `aria-expanded`, dialog roles and names), and a polite live region that announces every non-navigational action.

## L1-029: Design system: Standalone Folder Integrity
The design-system folder must have no runtime, validation, test, or build dependency on any other repository folder, so it can be copied or versioned independently. All fixtures, tokens, components, and tooling must live inside the folder, and no file in it may reference sibling repository paths.

## L1-030: Design system: Quality Gates and Deployment
A contract validator and a three-viewport browser test suite must gate an automated, path-filtered CI pipeline that deploys the built catalog to its own Azure Static Web App, with hosting configuration that preserves deep links, serves the manifest and preview page as raw static files, and applies security response headers.
