The same pipeline, twice

backend/src/Saturdaze.Application/Planning/WeekendPlanner.cs
public IReadOnlyList<ItineraryBlock> Plan(PlannerInputs inputs)
{
    var rng = new SeededRandomSource(inputs.Seed);
    var blocks = new List<ItineraryBlock>();
    foreach (var day in new[] { DayOfWeekend.Saturday, DayOfWeekend.Sunday })
    {
        var dayDate = day == DayOfWeekend.Saturday ? inputs.WeekendOf : inputs.WeekendOf.AddDays(1);
        var forecast = ForecastFor(inputs.Forecast, dayDate);
        blocks.AddRange(PlanDay(inputs, day, dayDate, forecast, rng));
    }
    return blocks;
}

First, the disqualifiers

WeekendPlanner.ScoreActivities

  • Already picked for this day
  • Typical duration longer than the gap
  • Both drives + 30 min of activity don't fit
  • Matches a disliked tag
  • Two or more members outside its age range

Then the points

ConditionScore
Rain or snow, and the activity is indoor+3
Sunny or warm, and the activity is outdoor+2
Round-trip drive > 40% of the gap−2
Every member inside the age range+2
Done last weekend / within four weekends−4 / −1
Try-new on, and never done before+3
Each liked tag+1

Per-day reseat: POST /api/weekends/{id}/days/{day}/regenerate

Pitfalls

  • Planning logic in a controller or page → move it to the handler or planner
  • System.Random or the clock in the planner → use the seeded source
  • A new query without the family scope → filter by the current family id
  • Inline planner numbers → change PlannerTimes, run the tests in Saturdaze.Application.Tests/Planning

Things to remember

  • Plan is idempotent; regenerate is the explicit reseat (ADR-003)
  • Page → token, controller → one line, handler owns the rules
  • Commitments first, gaps ≥ 90 min by score, then meals, errand, downtime
  • A seeded random source makes every plan reproducible
