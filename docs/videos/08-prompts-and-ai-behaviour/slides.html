Part 1 · The shared preamble

var preamble =
    $"You are a meticulous local-events researcher curating a weekend catalog for a family " +
    $"living in {ctx.HomeLocation}. You only return places and events within about " +
    $"{ctx.MaxDriveMinutes} minutes' drive of that home. You strongly prefer family- and " +
    $"kid-friendly options. Use the web_search tool to find REAL, currently-listed results " +
    $"from venue, tourism-board, municipal, and farm websites. Verify each row against a real " +
    $"page before including it; if you cannot verify it, leave it out. Never invent a venue, " +
    $"date, or URL.";

Persona · location · radius · family-friendly · the tool · verify, never invent

Part 2 · Type-specific rules

Events

  • Time-bounded: this weekend and the next, dates spelled out
  • No adults-only events
  • No ticketed concerts over $50 per adult

Activities

  • Mostly evergreen places for an afternoon
  • indoor true for bad-weather venues
  • weatherTags ⊆ sunny, warm, mild, cool, rain, cold

Restaurants

  • slot is Lunch or Dinner
  • wifeApproved: relaxed, quality, not too loud
  • notes: a short reason it earns its place

The user prompt is deliberately tiny

IngestionType.Events =>
    $"List family-friendly events near {ctx.HomeLocation} for the weekend of {weekend} and the " +
    $"weekend after. Return the JSON array only.",

All the weight sits in the system prompt, where Claude expects standing instructions. The user turn just names the catalog, the place and the date.

The schema is a contract

TypeParser requiresNatural keyUpserter truncates
Eventsname, startsOn, location (endsOn defaults to start)name | startsOn | locationname/location 200, category 80, url 500
Activitiesnamenamename 160, category 80, description 2000, mapUrl 500
Restaurantsname, slot ∈ Lunch | Dinnername | slotname 160, style 80, notes 500
all typeslatitude, longitude, address are optional: a location is stored only when both coordinates are present and in rangeaddress 300

A row missing a required field is rejected and counted; the rest of the batch still lands.

A new field is a three-place change

Prompt schema lineIngestionPrompts.cs
+
Reader / mappingIngestionResultParser.cs · CatalogUpserter.cs
+
Entity + migrationSaturdaze.Domain · Infrastructure

That is how latitude, longitude and address arrived (L2-099): the schema line, PayloadReader.GetGeo, and GeoLocation on each entity, in one change.

Prompt only

New field arrives in the JSON and is silently ignored.

Rename a required field in the prompt only

Every row is rejected; the audit row shows partial success or zero items.

Step 1 · Write the failing test

[Fact]
public void Restaurant_prompt_prefers_independents_over_chains()
{
    var prompt = IngestionPrompts.BuildSystemPrompt(IngestionType.Restaurants, Ctx);
    prompt.Should().Contain("chain");
}

Run dotnet test. It fails: the current prompt never mentions chains. That failure proves the test is real.

Step 2 · Change the wording

IngestionType.Restaurants =>
    $"{preamble}\n\nFind family-friendly restaurants. \"slot\" is \"Lunch\" or \"Dinner\". " +
    $"\"wifeApproved\" is true for relaxed, quality, not-too-loud places a discerning adult " +
    $"would happily return to (as opposed to purely kid-driven chains). \"notes\" is a short " +
    $"reason it earns its place. Prefer independent restaurants and exclude chains " +
    $"with more than twenty locations.\n\n" +
    $"{output}\n" +
    "[{\"name\": string, \"style\": string, \"slot\": \"Lunch\"|\"Dinner\", " +
    "\"wifeApproved\": boolean, \"driveMinutes\": integer, \"notes\": string}]",

Run the tests again. Green. The schema line did not change, so parser and upserter are untouched.

Model knobs · Saturdaze:Ingestion:Claude

SettingDefaultWhat it changes
Modelclaude-sonnet-5Foundry deployment name (must exist on the resource) or Anthropic model id
MaxSearches5max_uses of the web search tool: more verification, more input tokens
MaxTokens4096Output ceiling; too low cuts the JSON array mid-row
MaxContinuationTurns3How many pause_turn answers the client continues

Override any of them per process, e.g. Saturdaze__Ingestion__Claude__Model.

Reading the results

Console, every pass

One line per type: status, considered, upserted, rejected, searches, input + output tokens, error.

IngestionRun, real passes

Same numbers, permanent, plus the first error message when Failed.

Three numbers to watch

  • Considered vs rejected — did the model understand the schema?
  • Web search count — did it verify, or answer from memory?
  • Input tokens — what did the pass cost?

Pitfalls

Things to remember

Three layers. Wording in code; context and knobs in configuration.
One contract. Prompt schema, parser, upserter move together.
One order. Failing test → prompt → green → --dry-run → real run.
Dry runs cost tokens. Precise wording beats many iterations.
Zero items is a warning, not a quiet week.
