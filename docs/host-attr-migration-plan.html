Host-Attribute Tech-Debt Migration Plan

Scope: frontend/projects/components (the 29 sd-* library components) · Date: 2026-06-23 · Status: Proposed

Remove the native‑custom‑element carryover where every component reflects its input() values back onto the host element as HTML attributes (host: { '[attr.x]': '…' }), and replace it with idiomatic Angular data‑passing: inputs + template bindings for data, host classes for styling, and intentional test hooks for e2e.

1. Executive summary

Every Saturdaze UI component was ported 1:1 from a native custom element in docs/mocks/. Those mocks read their state from HTML attributes and styled via :host([attr]) selectors. The Angular port faithfully reproduced that by adding a host: {} block to each @Component that reflects each input() back onto the host as an attribute. The result is that ~70 host bindings across 25 components push data into the DOM that, in most cases, nothing reads — the template already renders the same value.

The migration is visually safe. The visual-diff harness compares rendered pixels, not the DOM. Converting :host([tone="sun"]) to :host(.tone-sun) with identical declarations produces byte-identical screenshots, so the committed baselines under *.spec.ts-snapshots/ do not need re-capture, and docs/mocks/ stays frozen as the design source. No external (global/page) SCSS reads these attributes, and the ADR-005 bottom-nav clearance invariant is untouched.

2. Where the debt comes from

The mocks use a tiny Web Components base class. Each element declares observedAttributes and styles itself with attribute selectors inside its shadow root:

// docs/mocks/components/sd-chip.js  (the source of the pattern)
class SdChip extends SdElement {
  static get observedAttributes() { return ["tone"]; }
  styles() { return `
    :host([tone="sun"]) { background: #FBEBC4; color: #8A6212; }
    :host([tone="sky"]) { background: #DCE9F1; color: #2C5F7A; }
    /* … */ `; }
  template() { return `<slot></slot>`; }
}

The Angular port kept the :host([tone]) SCSS verbatim, which forced a host block to keep the attribute present on the element:

// frontend/projects/components/src/lib/chip/chip.ts
@Component({
  selector: 'sd-chip',
  host: { '[attr.tone]': 'tone() === "default" ? null : tone()' }, // <- carryover
})
export class Chip { readonly tone = input<ChipTone>('default'); }

For data components the carryover is worse: the value is reflected to the host and rendered in the template, so the attribute is pure dead weight. sd-event-card reflects eight attributes; seven have no reader at all.

3. The four kinds of host binding

Auditing all 29 components classified every host binding into exactly one of these. The disposition follows from the kind:

3.1 Dead data mirror  DELETE

e.g. '[attr.subtitle]': 'subtitle() || null' where the template already has {{ subtitle() }}. Remove the host line — nothing else changes. This is the bulk of the cleanup (~35 bindings across 18 components) and is risk-free.

3.2 Style pivot  → CLASS

e.g. tone, variant, size, padding, full, disabled, interactive, static, checked, flush, compact, flat, locked, sticky-*, weather icon. The component's own SCSS reads them. Bind a host class and rewrite the selector. (~24 bindings across 12 components.)

3.3 Test-hook reflection  → TEST HOOK

e.g. title, name, day, label, value, type, drive, rating, favourite, vote, wifeapproved, icon-button icon. These are dead for styling but the e2e suite selects or asserts on them. They are the same debt as 3.1, but removing them requires updating the Playwright locator that depends on them.

Do not "fix" these by renaming [attr.title] to [attr.data-testid]. Reflecting data-testid="card-{{name}}" is the same input-to-attribute reflection wearing a different name. The data is already in the template, so the idiomatic Playwright move is a content/role query — locator('sd-event-card', { hasText: title }) or getByRole(...). Reserve an explicit, hand-authored data-testid for the few cases where the rendered content is not unique or not present (and apply it at the usage site, exactly like the existing <sd-button data-action="resend"> in check-email.page.html).

3.4 Genuine semantic / ARIA  KEEP

Only sd-toggle qualifies: [attr.role]="switch", [attr.aria-checked], [attr.tabindex]. These are not data reflection — they are the accessibility contract and stay. (Separately, sd-icon's :host([filled]) selector is set by consumers writing <sd-icon filled> directly; it is not a host binding and is out of scope.)

4. Idiomatic target patterns

4.1 Delete a dead mirror

// sd-hero — all three reflections are dead
host: {
  '[attr.greeting]': 'greeting()',
  '[attr.subtitle]': 'subtitle()',
  '[attr.cta]': 'cta()',
}
// host block removed entirely; greeting/subtitle/cta inputs + {{…}} untouched

4.2 Style pivot → host class

Recommended idiom: per-value [class.x] bindings, emitting a class for every value including the default. Per-value bindings are explicit, compose cleanly when a component has several style dimensions (e.g. sd-card has variant + padding + interactive), and are OnPush-friendly. Emitting the default value's class too (variant-default, size-md, tone-default) lets e2e select the default state positively — important because CSS has no class wildcard, so :not([variant]) cannot become :not(.variant-*).

// sd-button — before
host: {
  '[attr.variant]': 'variant() === "primary" ? null : variant()',
  '[attr.size]':    'size() === "md" ? null : size()',
  '[attr.full]':    'full() ? "" : null',
  '[attr.disabled]':'disabled() ? "" : null',
}
// sd-button — after
host: {
  '[class.variant-primary]':   'variant() === "primary"',
  '[class.variant-secondary]': 'variant() === "secondary"',
  '[class.variant-ghost]':     'variant() === "ghost"',
  '[class.variant-danger]':    'variant() === "danger"',
  '[class.size-sm]': 'size() === "sm"',
  '[class.size-md]': 'size() === "md"',
  '[class.size-lg]': 'size() === "lg"',
  '[class.full]':     'full()',
  '[class.disabled]': 'disabled()',
}
/* button.scss — mechanical selector rewrite */
:host([variant="secondary"]) button { … }   :host(.variant-secondary) button { … }
:host([size="sm"]) button { … }            :host(.size-sm) button { … }
:host([full]) { display: block; }          :host(.full) { display: block; }
:host(:not([full])) button { width: auto; } :host(:not(.full)) button { width: auto; }
:host([disabled]) button { … }             :host(.disabled) button { … }

Note on disabled: the inner <button [disabled]="disabled()"> keeps the real native disabled state — that is correct and separate from the host .disabled styling class.

Alternative for high-cardinality enums (e.g. sd-chip's 7 tones): a single computed() bound with [class] — protected hostClass = computed(() => 'tone-' + this.tone()); host: { '[class]': 'hostClass()' }. Use only when a component has a single style dimension, since a string [class] binding owns the whole attribute.

4.3 Test-hook reflection → content/role locator

// sd-event-card.ts — drop the reflection (title is rendered in the template)
host: { '[attr.title]': 'cardTitle() || null', … 7 more … }
// no host block
// e2e/pages/events.page.ts — was:
this.page.locator(`sd-event-card[title="${title}"]`)
// after: query by the title the card already renders
this.page.locator('sd-event-card', { hasText: title })

5. Cross-cutting safety findings

QuestionFinding
Does any external SCSS (global, app, page) select sd-* by attribute?No. Grep across all non-component SCSS returned zero matches. Only each component's own stylesheet uses :host([attr]).
Does the components-gallery page rely on reflected attributes?No. It passes data in via property/attribute bindings (variant="secondary", tone="primary"); it never reads reflected host attributes at runtime.
Does the migration touch the ADR-005 bottom-nav chrome invariant?No. The --sd-chrome-bottom rule uses CSS variables + env(), not attribute selectors. The bottom-nav-clearance.spec.ts guard is orthogonal. (The only bottom-nav change is deleting one dead [attr.active] mirror.)
Will the visual diff change?No pixels change. Playwright compares toHaveScreenshot() images, never the DOM. Identical computed styles ⇒ identical screenshots within the 0.5% tolerance.
Do committed baselines need re-capture?No. Run npm run test:visual to confirm; it should pass untouched.
Should docs/mocks/ be modified?No — leave frozen. The mocks are the design source-of-truth and baseline origin. Only the Angular components and SCSS change.

7. E2E locator migration

43 Playwright locators currently depend on reflected attributes. They split into two groups. Style-pivot selectors change mechanically to class selectors; data-hook selectors move to content/role queries (or an intentional data-testid). All e2e edits ship in the same PR as the corresponding component change.

7.3 Attribute assertions to convert

Beyond locators, several specs assert toHaveAttribute(...) on data mirrors. Convert each to assert the rendered content instead:

  • activities.spec.ts: toHaveAttribute('drive'|'why'|'tag', …) → assert the chip/callout text; toHaveAttribute('tone','indoor') → toHaveClass(/tone-indoor/).
  • restaurants spec: drive, wifeapproved → assert the badge text / a .wifeapproved class.
  • saved.spec.ts: rating → assert star count text; favourite → toHaveClass(/favourite/).
  • dialogs.spec.ts: text-input value/type → assert on the inner <input> via toHaveValue / getAttribute('type').
  • restaurants spec: vote-row vote → assert the selected vote button's state/text.

8. Phased rollout

Each phase is independently shippable, ordered by increasing blast radius. Phase 1 delivers the majority of the cleanup with zero risk; phases 2–3 each pair a component change with its e2e change in the same commit.

  1. Conventions & guardrail. Agree the class naming (variant-*, size-*, tone-*, boolean state = bare class) and the "emit a class for every enum value incl. default" rule. Optionally add an ESLint/CI check (or a small regression spec) that flags new '[attr.…]' data reflections in host: blocks so the debt cannot creep back.
  2. Delete all dead mirrors. The DELETE bindings across ~18 components (anticipate, hero, empty, top-bar, bottom-nav, icon, plus the dead lines in the mixed components). No SCSS, no e2e, no template change. Ship as one PR; npm run test:visual + behavior specs stay green untouched.
  3. Migrate style pivots to host classes. The CLASS components (button, card, chip, avatar, icon-button, dialog, section, list-item, split-view, timeline-block, toggle, weather-day). Each: rewrite host bindings + :host([x])→:host(.x) SCSS + the §7.1 style-pivot e2e selectors, together. Run visual + behavior after each.
  4. Remove test-hook reflections. The TEST bindings. Migrate the §7.2 / §7.3 Playwright locators and assertions to content/role queries first (or add intentional data-testids at usage sites), then delete the reflection. This is the highest-touch phase and can be staged component-by-component.
  5. Final sweep. Confirm no '[attr.…]' remains except the §3.4 KEEP set (toggle ARIA) and genuine inner-element bindings. Update component header comments that describe the old "mirrors sd-*.js" attribute contract.

9. Verification checklist

Run after every phase (and per-component within phases 2–3):

# component library + app still build (warnings are errors here)
npm run build -- components && npm run build -- saturdaze --configuration development

# unit tests (Vitest)
npm test

# from e2e/ — behaviour must stay green (this is where e2e selector edits land)
npm run test:behavior

# pixel parity — MUST pass with NO baseline re-capture
npm run test:visual

# bottom-nav invariant guard (only relevant if nav is touched; it isn't, but cheap)
npx playwright test tests/regression/bottom-nav-clearance.spec.ts

If test:visual reports a diff, stop — it means a class rewrite changed a computed style (e.g. a selector specificity slip or a missed :host([x])). Fix the SCSS; do not re-baseline, because the design has not changed.
