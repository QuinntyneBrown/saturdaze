Foundation

Theming

A theme is a set of values for the alias tokens, nothing more. Components read roles such as "brand fill" and "card surface", so the same markup works in light, in dark, at higher contrast and under a different brand without a single component rule changing.

Overview

Saturdaze's tokens follow the Fluent UI v9 model the product adopted in ADR-013. There is one stylesheet, tokens/tokens.css, and every page, component and export reads it. Theming happens in one tier only, the alias tier:

  • Light is the default, on :root. It is what the product ships today.
  • Dark is built from the same roles, not inverted from light. The mocks and the product have no dark theme (D25); this one is a worked proposal that passes AA everywhere this site shows a pair.
  • Preferences (more contrast, forced colours, reduced motion) adjust a handful of alias tokens on top of whichever theme is active.

Use the toggle at the top of the navigation (or press t) to switch this whole site between themes. Your choice is remembered on this device.

How themes work

tokens.css declares each alias token four times. The selectors decide which block wins:

SelectorWhen it appliesWhy
:rootAlways: the light values.The default, and the fallback for any token a theme does not override.
[data-theme="light"]On any element, including <html>.A light subtree inside a dark page (the side-by-side panels on this site), and a way to force light against the OS preference.
[data-theme="dark"]On any element.An explicit dark choice for the page or a subtree.
@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }The OS asks for dark and the page has not forced light.Follows the device without script, so the first paint is already in the right theme.

The last two blocks hold identical declarations. Edit one, then copy it into the other; the contrast checker reads both, so a drift between them shows up as a failing pair.

Each theme also sets color-scheme (light or dark). That tells the browser to draw native parts of the page to match: scrollbars, the date and time pickers in commitment dialogs, the checkbox and radio fills, autofill backgrounds and the default canvas before the stylesheet loads.

<html lang="en">                        <!-- follows the device -->
<html lang="en" data-theme="dark">      <!-- always dark -->
<section data-theme="light">…</section> <!-- a light island on a dark page -->

Token tiers

Three tiers, each allowed to read only the one below it. A value appears once as a global, gets a meaning as an alias, and gets scoped to one component as an --sd-* token.

TierNamesExampleWho reads it
1. Global--globalColor*--globalColorCoral500: #bf5130Alias tokens only. Never a component, never a page.
2. Alias--color*, --spacing*, --fontSize*, --borderRadius*, --shadow*, --duration*, --zIndex*, --layout*, --target* …--colorBrandBackground: var(--globalColorCoral500)Components and pages. Themes override this tier and nothing else.
3. Component--sd-<component>-*--sd-btn-bg: var(--colorBrandBackground)One component, declared in assets/components.css; always set to an alias token.

Real examples from components.css

/* Tier 3 defaults on the base class, overridden per variant */
.btn         { --sd-btn-bg: transparent; --sd-btn-fg: var(--colorNeutralForeground1); … }
.btn--primary { --sd-btn-bg: var(--colorBrandBackground);
                --sd-btn-fg: var(--colorNeutralForegroundOnBrand);
                --sd-btn-bg-hover: var(--colorBrandBackgroundHover); }

/* A disc picks a palette by role, not by colour */
.disc--sun  { --sd-disc-bg: var(--colorPaletteSunBackground1); --sd-disc-fg: var(--colorPaletteSunForeground1); }

/* A local re-skin overrides component tokens, never the component rule */
.cover__edit { --sd-btn-bg: var(--colorNeutralBackgroundAlpha); --sd-btn-bg-hover: var(--colorNeutralBackground1); }

/* The map, which used to carry 21 inline hex fills (D18) */
.map { --sd-map-land: var(--colorPaletteLeafBackground1); --sd-map-water: var(--colorPaletteSkyBackground3); … }

So there are three levers, each for a different job: change a global to adjust a hue everywhere it is used; change an alias (in a theme block) to change what a role looks like; change a component token to re-skin one instance. None of them edits .btn itself.

The dark theme

Dark was built role by role from the light theme's intent, not by inverting its colours. Four decisions shape it:

  • Warm umber surfaces that lighten as they rise. The canvas is the darkest step and every layer above it is a little lighter, so elevation still reads where shadows barely show. The umber keeps the cream warmth of the light theme instead of going to cold grey.
  • Coral 300 fill with a dark label. Coral 500 on near-black is murky and white on coral 300 fails, so the brand fill lightens to coral 300 and its label flips to coral 950. Links, the focus ring and the current-tab underline use the same light coral.
  • Status tints deepen. Pale success, warning and danger backgrounds become deep tints (forest 900, sun 900, terracotta 900) with light ink on top, so a locked day or an error still stands out without glowing.
  • Shadows get stronger, scrims get darker. Shadow alphas rise from 4 to 12% ink to 30 to 55% black, and the dialog scrim goes from 40% ink to 60% black.

Adding a brand theme

A brand theme (a partner city, a seasonal look) is one more block that overrides brand alias tokens. It never touches components, and it keeps the neutrals and status colours so a locked block and an error look the same in every brand.

  1. Add the new ramp to the global tier (--globalColorHarbour100 … --globalColorHarbour950), or reuse an existing one.
  2. Add [data-theme="harbour"] with the --colorBrand* tokens, --colorStrokeFocus2 and --colorNeutralForegroundOnBrand. Add a [data-theme="harbour-dark"] (and its prefers-color-scheme twin) if it needs a dark form.
  3. Add its pairs to tokens/contrast-pairs.json and run the contrast check until every pair passes in every theme.
  4. Regenerate tokens.json and document the theme here.

Contrast and forced colours

Two device preferences adjust the active theme rather than replacing it.

More contrast

Under prefers-contrast: more the decorative strokes become the accessible stroke and secondary text steps up one level, so card edges, dividers and meta text all clear their minimums with room to spare.

@media (prefers-contrast: more) {
  :root {
    --colorNeutralStroke1: var(--colorNeutralStrokeAccessible);
    --colorNeutralStroke2: var(--colorNeutralStrokeAccessible);
    --colorNeutralForeground2: var(--colorNeutralForeground1);
    --colorNeutralForeground3: var(--colorNeutralForeground2);
  }
}

Forced colours

In Windows High Contrast and other forced-colour modes the browser replaces most colours with the user's system palette. The tokens hand the parts it would otherwise miss to system colours: the focus ring becomes Highlight and every edge becomes CanvasText, so field borders, card edges and the switch track stay visible.

@media (forced-colors: active) {
  :root {
    --colorStrokeFocus2: Highlight;
    --colorNeutralStroke1: CanvasText;
    --colorNeutralStroke2: CanvasText;
    --colorNeutralStrokeAccessible: CanvasText;
  }
}

States that rely on a fill alone disappear in forced colours, which is why pressed filter chips also take a border (D26), filled icons change shape, and the current tab carries aria-current and an underline rather than only a tint.

Reduced motion works the same way, on the duration tokens; see Motion.

Consuming tokens.json

tokens/tokens.json is a W3C Design Tokens (DTCG) export of tokens.css for tools that cannot read CSS: Figma plugins, Style Dictionary, native apps. It is generated; never edit it by hand. After changing tokens.css, run from the repo root:

python docs/design-system/tokens/export_tokens.py

From custom property to JSON path

The camelCase name is split at each change of case. The first two words become groups and the rest stays together as the token's key; a name with one word and a number splits there.

Aliases and the dark theme

A token whose value is exactly one var() exports as a DTCG alias in braces, with the computed value alongside. Light is the $value; the dark value sits under $extensions["com.saturdaze"].themes.dark:

"color": { "brand": { "background": {
  "$type": "color",
  "$value": "{global.color.coral500}",
  "$extensions": { "com.saturdaze": {
    "css": "--colorBrandBackground",
    "resolved": "#bf5130",
    "themes": { "dark": { "$value": "{global.color.coral300}", "resolved": "#f59c7c" } }
  } }
} } }

Every leaf carries its css name, so a tool can always map back to the custom property. The export covers the :root and [data-theme="dark"] blocks; the responsive retunes (columns, gutters, display sizes) and the preference blocks stay in CSS, and the Layout and Typography pages list them.

The product's TypeScript theme

The Angular app does not read this folder. Its tokens live in frontend/projects/components/src/lib/tokens/ as a typed Fluent-style theme (global/ ramps, alias/ roles, createLightTheme(brand)), and npm run tokens generates styles/_tokens.scss and tokens.ts from it (ADR-013).

  • Same names. Wherever the product has a token, this system uses its exact custom-property name, so a rule copied from here works there.
  • Different values where AA required it. The product inherited the mock values; this system changed the ones that failed (focus ring, faint and soft text, accessible strokes, danger fill: D03 to D08). Carrying a fix over means changing the TypeScript theme and regenerating, never editing _tokens.scss.
  • Light only. The product ships the light theme (D25). A dark theme there would be a createDarkTheme(brand) beside createLightTheme, using the role mapping on this page.
  • Runtime themes. The product's [sdThemeProvider] directive writes a partial theme onto its host as custom properties, which is the same mechanism as the harbour example above.

Usage

  • Read tokens by role: --colorBrandForeground1 for text, --colorBrandBackground for fills, --colorBrandStroke1 for borders, even when two roles share a value today.
  • Never read a --globalColor* token from a component or page; the theme cannot reach it.
  • Re-skin one instance with its component tokens; re-theme a subtree with data-theme; never fork a component rule per theme.
  • Anything drawn on a photo uses the static tokens (--colorNeutralForegroundStaticInverted, --colorBackgroundOverlayStrong), because the photo does not change with the theme.
  • Check a new pair in both themes before using it. The contrast pairs on component pages are live in both.

Tokens

Theming owns no tokens. It explains the theme blocks; colour tokens and their values are owned by the Color page.
