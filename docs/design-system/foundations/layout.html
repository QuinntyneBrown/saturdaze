Layout

Overview

Saturdaze is a phone app first: most planning happens on a phone on Friday night or Saturday morning. Layout starts at one column at 360px and adds structure at four rem breakpoints, on a 4, 8 then 12 column grid whose gutters and margins grow with it.

  • Four breakpoints: 380, 576, 720 and 1024px, written in rem.
  • A responsive grid: 4 / 8 / 12 columns, 16 / 24 / 32px gutters, margins equal to the gutter.
  • Seven container widths from the 240px sidebar to the 1120px content column, plus the chrome heights and page spacing.
  • Four page templates: app shell, auth, admin and the weekend planner.

Breakpoints

Saturdaze is designed at 360px first and adds layout as space allows: every rule is a min-width query except the two small-phone retunes. The breakpoints are in rem (D24), so a reader with a larger default font reaches the phone layout sooner instead of getting cramped text in a desktop layout.

TokenValueWhat changes at and above it
--layoutBreakpointSm (380px)Small phones end. Below it the four largest type sizes step down, and the site bar hides its secondary links so the brand and sign-in button fit.
--layoutBreakpointMd (576px)Description lists put the label in a column beside the value; photo pickers go three across.
--layoutBreakpointLg (720px)The top bar replaces the bottom nav. Dialogs change from a bottom sheet to a centred modal and their footer buttons move into one right-aligned row. The grid goes to 8 columns with 24px gutters, section spacing to 40px, the auth card to 32px padding, and card grids to two across.
--layoutBreakpointXl (1024px)The Weekend planner puts the day beside a sticky map. Admin navigation becomes a 240px sidebar. The grid goes to 12 columns with 32px gutters, card grids to three across, the two days side by side, and display type steps up.

CSS media queries cannot read custom properties, so components.css repeats the rem values literally (@media (min-width: 45rem)). The tokens are the reference; keep them and the queries in step. Upper bounds use the value just below the next breakpoint (max-width: 44.9375rem, 23.6875rem) so no width matches two ranges.

Navigation and dialogs both switch at 720px on purpose: a phone-sized window gets the thumb-reachable bottom nav and bottom sheets together, and a tablet or desktop gets the top bar and centred dialogs together. See responsive for each component's behaviour.

Section and page spacing

Three tokens set the rhythm of a whole page, outside any component.

TokenValueUsed for
--layoutSpaceSection (32px, 40px from 720px)Between the sections of a page: the cover and the planner, Saturday and Sunday on a phone, groups of cards on Ideas
--layoutSpacePage (64px)Page bottom padding from 720px, landing bands, desktop hero padding (D16)
--layoutSpacePageLarge (80px)Before the site footer on the landing and legal pages

On phones the app's main area also clears the floating bottom nav: its bottom padding is the nav height plus 12px offset plus 24px plus the safe-area inset, so the last card is never hidden behind the nav (ADR-005 covers the iOS chrome handling).

Usage

  • Mobile first. Write the 360px layout, then add min-width queries at the four breakpoints. Do not invent breakpoints for one component; if something breaks between them, fix the component's flexibility.
  • Use the containers. Pages start with .container or .container--stack; no ad-hoc max-width on page sections.
  • No horizontal scroll at 320px. Every grid track is minmax(0, 1fr), long words wrap (overflow-wrap: anywhere on names and URLs), media is max-width: 100%. The one exception is .scroller-x, a deliberate horizontal list of chips or photos on phones, which bleeds to the screen edge and becomes a wrapping row from 720px.
  • Margins equal gutters. Never set page padding by hand; --layoutMargin follows the gutter.
  • Respect the chrome. Fixed and sticky elements clear the top bar, bottom nav and safe-area insets with the layout tokens, never with magic numbers.
  • Reorder with care. Visual order follows source order. The planner's map-first phone layout is the one exception, and the map duplicates information the day list carries, so keyboard and screen reader order (day first) loses nothing.

Accessibility

  • Reflow (1.4.10). Every page works at 320px CSS width (a 1280px window at 400% zoom) without two-dimensional scrolling. Tables are the exception the criterion allows, and they scroll inside their own wrapper.
  • Resize text (1.4.4). Breakpoints in rem mean that enlarging the browser's text size moves the page to a narrower layout before anything overlaps (D24).
  • Orientation (1.3.4). No layout is locked to portrait or landscape; a phone on its side gets the 720px layout if it is wide enough.
  • Focus not obscured (2.4.11). The sticky top bar and floating bottom nav must not cover the focused element. The mocks set scroll-padding-top to the top bar height plus 16px; the app should do the same with --layoutTopBarHeight, and add scroll-padding-bottom for --layoutBottomNavHeight on phones, which the mocks do not yet.
  • Landmarks. Each template has one header (top bar), one nav per navigation (labelled), one main, and a footer where there is one; the bottom nav and the top bar are the same nav landmark at different widths.
