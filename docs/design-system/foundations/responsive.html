Foundation

Responsive

Most weekends get planned on a phone, often one-handed on a Friday evening. Every screen is designed at 360px first; wider screens add columns, labels and side-by-side views, never features.

Overview

  • Mobile first. Base styles are the phone layout. min-width queries add space, columns and labels as the screen grows.
  • The same product at every width. A tablet sees the same actions as a phone, laid out differently. Nothing is only on desktop.
  • Breakpoints in rem (23.75, 36, 45 and 64rem), so a person who has raised their browser's text size gets the layout that fits their text, not their pixels (D24).
  • Layout follows tokens. Columns, gutters and margins change in tokens.css at each breakpoint; components read --layoutGutter and --layoutMargin rather than writing their own numbers.
  • Type is fixed, not fluid. Sizes come from the scale and change only at the ends (under 380px and from 1024px), so zoom always works.

Breakpoints

Custom properties cannot be used inside @media, so the values are written out in each query. The tokens (--layoutBreakpointSm/Md/Lg/Xl) exist so scripts and docs can read them; their values are on Layout.

Touch and pointer

  • Hover only where hover exists. Every :hover rule sits inside @media (hover: hover), so a tap on a phone never leaves a button tinted or a card lifted. Documentation forces the same look with data-state="hover".
  • Nothing hides behind hover. Anything revealed on hover is also revealed on :focus-within for keyboards, and stays visible under (hover: none) for touch. The timeline's Swap and Lock buttons were hover-only in the mock, so an iPad at 820px could not reach them (D21).
  • Targets do not grow with pointer: coarse. They are already at least 24px everywhere (--targetMin) and 44px for phone page actions, dialog buttons and form fields (--targetComfortable). See Accessibility.
  • No gestures without buttons. There is no swipe-to-delete or drag-to-reorder; every action has a visible control.
  • Thumb reach. On phones the primary action goes where the thumb is: full width at the top of the page actions, at the top of a sheet's button stack, and the navigation at the bottom.

Safe areas and the viewport

  • Safe areas. Fixed and full-bleed elements add env(safe-area-inset-*): the app's top padding, the bottom padding that keeps content above the nav, bottom sheets and the toast region. The page meta sets viewport-fit=cover so those values are non-zero on notched phones.
  • Bottom chrome (ADR-005). iOS Safari's toolbar can cover a fixed element at the bottom of the screen. The bottom nav sits at calc(12px + max(env(safe-area-inset-bottom), var(--sd-chrome-bottom))). --sd-chrome-bottom is measured by a VisualViewport listener in the product's main.ts before Angular starts. It is the larger of the two, not the sum, because Safari's toolbar already covers the home indicator. Read ADR-005 and run its regression test before changing the bottom nav.
  • Full height is 100svh. Auth screens, the admin shell and the dialog's 88svh cap use the small viewport unit, the height with the browser bars expanded, so nothing important ends up under them. ADR-005 records why lvh and dvh arithmetic failed for the nav.
  • No orientation lock. Landscape phones get the phone or tablet layout their width calls for.
.bottom-nav {
  /* ADR-005: clear whichever bottom obstruction is present (not additive). */
  bottom: calc(var(--spacingVerticalM) + max(env(safe-area-inset-bottom, 0px), var(--sd-chrome-bottom, 0px)));
}
