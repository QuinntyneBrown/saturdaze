Error page

When a whole page cannot be shown, the error page says what happened in plain words, keeps the family inside Saturdaze, and offers one way back. It is an empty state with a status code, centred in the app shell.

Overview

Use an error page only when the page itself cannot render: the route does not exist, the account may not see it, the server failed before any content came back, or the device is offline. When one part of a page fails (the forecast, a photo, one save), keep the page and show an alert or inline message in that place instead. A form error is never an error page.

  • 404, not found: an old link, a deleted weekend, a typo. Also the answer for another family's data (see below).
  • 403, not allowed: the account is signed in but the page is for administrators (Saturdaze Admin).
  • 500, something went wrong: our fault. Shows a reference id the family can send us.
  • Offline: no connection. Offers to try again; no status code.
Family-scoped data answers 404, not 403. A weekend, member or errand that belongs to another family returns "We can't find that page", so a guessed URL never confirms that someone else's data exists (AGENTS: family-owned data stays scoped to the current family). 403 is only for roles, such as a family account opening Saturdaze Admin.

Anatomy

  1. Page frame.error-page: a centring grid, 60vh tall, page padding (64px top and bottom, 16px or more at the sides), inside the normal app shell.
  2. Status.error-page__status: the code in --typographyLargeTitle, --colorBrandForeground1. Decorative (aria-hidden); the title says it in words.
  3. Title.empty__title, the page's h1: what happened, not the code.
  4. BodyWhy, in one sentence, and that nothing was lost when that is true.
  5. RecoveryOne primary action that fixes the situation. 500 adds the reference id under it (.empty__note + .empty__code).

In the app shell

The error page keeps the top bar (720px and up) or the bottom nav (phones), so every other part of Saturdaze is one tap away. On Saturdaze Admin it keeps the admin navigation; on signed-out routes it keeps the site bar.

Sizes

One size: the error page fills the main column of the app shell at every width.

States

The page is static; its recovery action carries the states. "Try again" goes busy while it retries and, if the retry fails, the page stays and the reference id updates. Pointer and focus states are forced with data-state.

  • Offline retries on its own when the browser's online event fires, and replaces itself with the page; "Try again" is for people who do not want to wait.
  • Retry failed keeps the same page, announces "Still not working" in a polite live region, and shows the new reference id.

Responsive behaviour

  • Under 720px the shell shows the bottom nav and no top bar; from 720px it shows the top bar. The error page itself is the same at every width.
  • The card fills the column minus the 16px margin on a phone and caps at 480px, centred, from 576px.
  • The 60vh minimum height keeps the card near the optical centre on tall phones; with a short landscape viewport it falls back to the page padding.
  • The reference id may wrap onto its own line; it never truncates.

Theming

The error page reads the empty state tokens plus one of its own: the status code in --colorBrandForeground1, which lightens to coral 300 in the dark theme. It never uses the danger palette: a missing page is not an alarm, and red would make a 404 feel like the family did something wrong.

Accessibility

Role and pattern

A normal page: the title is the page's h1 (the status code is aria-hidden), inside <main>, with the shell's landmarks around it. The document <title> names the error too: "Page not found · Saturdaze". The server returns the real HTTP status so assistive tools, bookmarks and search do the right thing. No APG pattern applies.

Keyboard

KeyAction
TabSkip link, shell navigation, then the recovery action.
Enter / SpaceFollows or activates the recovery action.

Focus

After a client-side navigation lands on an error, move focus to the h1 (with tabindex="-1") so screen-reader users hear what happened, the same as any route change. After a failed retry, keep focus on "Try again".

Labelling

Say the problem in words; "404" alone is jargon. The reference id is plain selectable text, so it can be copied by hand or read aloud on a call; do not render it as an image or put it in a tooltip.

Motion

None. The busy "Try again" spinner keeps turning under reduced motion, like every spinner (D29).

Touch

The recovery action is a medium button (40px), centred, with nothing else within reach. The bottom nav keeps its 44px-plus items.

Content

  • Title says what happened from the family's side: "We can't find that page", "This page is for administrators", "Something went wrong on our side", "You're offline".
  • Body says what is still fine, then what to do: "Your weekend is safe. Try again in a minute."
  • Own server errors ("on our side"). Never blame the person, never "Oops", never a stack trace or an exception name.
  • The action is a destination or "Try again". One action only; the shell already offers the rest.
  • Reference ids are short and grouped (SD-7F3A-21C9) so they can be read out loud.
