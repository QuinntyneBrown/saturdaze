Dialog

A dialog asks for one thing and nothing else: lock this block, regenerate the weekend, edit Mae, remove a member. It slides up as a sheet on phones and sits centred from 720px.

Overview

Every button-triggered edit in Saturdaze opens a dialog or goes to a screen; pages never grow inline forms. Use a dialog when the task is short (one to four fields), the person should stay in context, and the page behind should not change until they decide. The mocks draw 39 of them (D1 to D29, AD1 to AD6).

  • Use a toast for news that needs no answer ("Saved"), a menu for a list of commands, and a tooltip for a hint.
  • Use a full screen when the task is long, needs its own URL, or may be left half done (the admin place editor).
  • One dialog at a time. A confirmation started from a dialog (Remove in D17) replaces it; it never stacks on top.

The specimens on this page are drawn in the page flow (.dialog--specimen), so they carry role="dialog" and a label but not aria-modal. A shipped dialog is opened by Angular CDK Dialog, which adds aria-modal="true", the scrim, the focus trap, Esc and focus return.

Anatomy

  1. Title.dialog__title, --typographyTitle2, an h2. Referenced by aria-labelledby.
  2. Subtitle (optional).dialog__sub: the consequence or context in one line. Referenced by aria-describedby.
  3. Close.dialog__close: ghost small icon button, aria-label="Close". Always present.
  4. Body (optional).dialog__body: wells, fields, lists, a sunk recap card; 16px gap. Confirmations may have none.
  5. Actions.dialog__actions: safe action then primary or danger; .dialog__actions-left holds a warn-text action.
  6. Panel and scrim.dialog__panel on --colorNeutralBackgroundRaised, --shadow28, --borderRadiusXLarge; .dialog__scrim dims the page.

Sizes

Two widths. Default is 480px (--layoutDialogWidth) for confirmations and details; .dialog--wide is 520px (--layoutDialogWidthWide) for forms with side-by-side fields (D17, D23, D28). Height follows content up to 88% of the viewport, then the panel scrolls with its header in view. On phones both widths are the full screen width.

States

The dialog itself has three states: open, busy and closed. Its parts carry the rest: the focused control draws the ring, an invalid field shows its error, a busy button spins.

  • Open: scrim over the page, panel rises 4px and fades in over --durationNormal; the page behind is inert and does not scroll.
  • Busy: aria-busy="true" on the dialog fades and blocks the body; the pressed button spins; Esc, Close and the scrim are ignored until the request settles, so a half-saved edit cannot be dismissed.
  • Invalid: errors appear under their fields on submit and focus moves to the first invalid field. The dialog stays open. See forms.
  • Failed: a request error shows as an inline message at the top of the body; the person's input is kept.

Responsive behaviour

  • Under 720px: bottom sheet. Full width, anchored to the bottom, top corners rounded, a grab handle, 20px padding plus the safe-area inset so the buttons clear the iPhone home indicator. Buttons stack full width at 44px with the primary or danger on top, under the thumb; a .dialog__actions-left action drops into the stack.
  • From 720px: centred modal. 480 or 520px wide, all corners rounded, 24px padding, buttons in one right-aligned row at 40px with the primary last and the warn-text action far left.
  • Tall content scrolls inside the panel (max 88% of the small viewport height, svh), so the browser's own chrome never hides the actions on iOS.
  • The handle is decorative: the sheet does not need a drag gesture. Close, Cancel, Esc and a tap on the scrim all dismiss it (2.5.7).

Theming

The panel reads --colorNeutralBackgroundRaised, the highest surface in both themes: white in light, the lightest umber in dark, so the dialog rises above the cards behind the scrim. The scrim is --colorBackgroundOverlay, deeper in dark so the panel still separates. Width is themable through --layoutDialogWidth and --layoutDialogWidthWide; nothing in a dialog uses a raw colour, including the scrim that was rgba() in the mocks (D17).

Accessibility

Role and pattern

APG Dialog (Modal). The product opens every dialog through Angular CDK Dialog with the shared options (autoFocus: 'first-tabbable', restoreFocus: true), which renders role="dialog" aria-modal="true" aria-labelledby="<title id>", traps focus, makes the page behind inert, closes on Esc and returns focus to the trigger. Destructive confirmations use role="alertdialog" (APG Alert Dialog). Never hand-roll a modal.

Keyboard

KeyAction
Tab / Shift+TabMoves through the dialog's controls and wraps; focus never reaches the page behind.
EscCloses the dialog like Cancel and returns focus to the button that opened it. Ignored while busy.
EnterIn a form dialog, submits from any text field. Elsewhere activates the focused button.
SpaceActivates the focused button.

Focus

On open, focus goes to the first tabbable element, which is the Close button: a safe place for every variant, including destructive ones, so an accidental Enter never deletes. Form dialogs may move it to the first field. On close, focus returns to the trigger; if the trigger is gone (the member was removed), it goes to the section heading that held it. The ring is the shared 2px --colorStrokeFocus2 and stays inside the panel's padding, never clipped.

Labelling

aria-labelledby points at the title; aria-describedby at the subtitle when it states the consequence ("Future weekends will not plan for her."). The close button is aria-label="Close". A busy dialog announces its progress through the button's aria-busy and a polite live region ("Saving"), not by changing the title.

Motion

The panel rises 4px and fades in over --durationNormal (sd-rise). Under prefers-reduced-motion the duration is zero and the dialog simply appears. Closing has no animation, so focus return is immediate.

Touch

Phone footers are 44px full-width buttons. The close button is 32px with a 4px negative margin into the corner; it clears the 24px minimum and has no neighbours within 8px. Tapping the scrim cancels, except while busy.

Content

  • Confirmations ask a question that names the thing: "Remove Mae from the family?", "Regenerate Saturday?", "Lock La Marina for Saturday lunch?". Never "Are you sure?".
  • The subtitle says what happens next or what stays: "Locked blocks stay where they are." "Sunday will not change."
  • The primary button repeats the verb: Regenerate, Remove, Approve, Add to Saturday. Cancel is always "Cancel"; a success dialog's only button is "Done".
  • Success titles state the result: "Added to Sunday at 9:15", "Thanks, it is in the queue".
  • Edit titles name the person or thing: "Edit Mae", "Edit Swim lessons", "Add a family member".
