Inline message

An inline message sits right under one field and talks about that field only: a hint before typing ("How we greet you."), an error after ("This address isn't on the image allow-list."), or a quiet confirmation when a check passed.

Overview

  • Hint (.field__hint): what the field wants, before anyone types. Formats, limits, why we ask.
  • Error (.field__error): what is wrong and how to fix it, with an alert icon. Pairs with aria-invalid="true" on the field.
  • Success (.field__success): a check that passed and is worth saying out loud, such as coordinates that were found on the map. Most fields never show one.

A message about the whole form or the account is an alert; a summary of several field errors is the error summary in forms. The field itself is documented in form field and text field; password strength uses the meter on progress bar.

Anatomy

  1. Field in erroraria-invalid="true" turns the border to --colorStatusDangerForeground3; the focus halo turns red too.
  2. Error14px alert icon and caption-size medium text in --colorStatusDangerForeground1, 4px gap. The icon makes it more than colour.
  3. HintCaption size, --colorNeutralForeground2. Stays visible under the error when it helps fix it.

A disabled field keeps its hint (it may explain why it is disabled) but never shows an error or success: the person cannot act on it.

When to validate

  1. While typing the first time: say nothing. An error that appears after one letter of an email is noise.
  2. On blur: check the field. Show the error under it and set aria-invalid="true".
  3. Once a field has an error: re-check on every input, so the error clears the moment it is fixed. Never add a new error while typing.
  4. On submit: check everything, show each field's error, and show the error summary at the top of the form with focus on it (forms).
  5. Checks with no blur, such as a file chosen in a picker: show the error at once in a role="alert" message (the profile photo dialog does this).

Responsive behaviour

  • Messages wrap under the field at the field's width; they never truncate and never sit beside the field.
  • In a two-column row (.field--row) each message stays under its own field, so rows can end at different heights.
  • A counter in .field__foot keeps its place at the end of the line; the hint wraps before it.

Theming

Messages read status and neutral foreground tokens directly; there are no component tokens. The invalid field reads --sd-field-border, which aria-invalid sets to --colorStatusDangerForeground3. In the dark theme the danger and success foregrounds switch to their light steps on the dark field surface.

Accessibility

Role and pattern

Messages are plain paragraphs linked to the field with aria-describedby, error first: aria-describedby="age-err age-hint". Every id listed must exist in the DOM: the Angular sd-text-input hides the hint while an error shows but still lists the hint's id. Errors use aria-invalid="true" on the field (3.3.1). No APG widget pattern applies.

Keyboard

KeyAction
TabLeaving a field validates it; the message is read when focus returns.
EnterSubmits the form; all errors appear and focus moves to the summary.

Focus

Validation never moves focus on blur; the person is already on the next field. On submit focus goes to the error summary, whose links move focus to each invalid field.

Labelling

The error repeats enough of the field to stand alone in the summary ("Enter Mae's age as a number, like 5."). Do not use role="alert" on errors shown on blur: it would interrupt the label of the field the person just moved to. The icon is decorative.

Motion

The border colour changes over --durationFast; messages appear without animation, so nothing slides under the cursor.

Touch

Messages are not targets. Links inside a hint ("Copy the coordinates from any map app") keep the 24px minimum.

Content

  • Hints: short and specific, a full stop: "How we greet you.", "JPG, PNG or WebP, up to 2 MB.", "Under 18 counts as a kid."
  • Errors: say how to fix it, with an example when the format is the problem: "Enter Mae's age as a number, like 5." Not "Invalid input".
  • Name the actual problem: "That file is not a JPG, PNG or WebP image." Not "Upload failed".
  • No blame, no "please", no exclamation marks.
  • Success: what was confirmed, not praise: "Found: Port Credit Memorial Park." Not "Looks good!"
