Radio group

A radio group asks for exactly one answer from a short, visible set: which day an errand goes on, how far the family will drive. Every option is on screen, so nobody has to open a menu to compare them.

Overview

Use a radio group when the person must pick one option and seeing all of them helps the choice. Both forms are real <input type="radio"> elements sharing a name, so the browser handles selection, arrow keys and form submission.

  • Segmented radio (.seg-radio) is the form the mocks use: two or three one-word options in a pill track. "Which day" in Add an errand (D7: Saturday, Sunday, Either), Edit a commitment (D18) and Add an idea to a day (D28).
  • Radio list (.choice-group of .check rows) is for options that need more than a word, or a description under each, or more than three options.

Use a checkbox when several answers can be true, a switch for a setting that is on or off, a select when there are more than about six options, and segments (.segments) when the control switches what the page shows rather than answering a question in a form.

Anatomy

  1. Group label.field__label with an id, referenced by aria-labelledby (or a <legend> in a fieldset). It names the question.
  2. Track.seg-radio: --colorNeutralBackground3, 4px padding, pill radius, equal columns (--3 for three).
  3. Option.seg-radio__opt, a <label> 36px tall. The real radio fills it at zero opacity, so the whole pill is the target.
  4. Selected optionWhite pill (--colorNeutralBackground1) with --shadow4 and the label darkened to --colorNeutralForeground1.

Variants

Pick the segmented form when every option is one short word and there are two or three of them. Pick the list when options need a sentence, a description, or there are four to six.

Sizes

One size. The native radio is 18px with the whole label as its target; a segmented option is 36px tall and as wide as its column.

States

Hover and focus are forced with data-state so they can be reviewed without a mouse. On the radio list, data-state="focus" goes on the input, which is where a real :focus-visible lands; on the segmented radio it goes on the option label, which draws the ring around the pill. Checked, disabled and invalid use the real attributes.

Both themes

Budget
Budget
  • Checked is the only selected state; a group can start with nothing checked when there is no safe default (D18 Add a commitment), and must then say so on submit.
  • Disabled uses the native attribute (50% opacity, not focusable). Disable the whole group with <fieldset disabled>; disable one option only when the reason is shown nearby.
  • Invalid sets aria-invalid="true" and links the .field__error with aria-describedby on the group.

Responsive behaviour

  • The segmented radio is always full width with equal columns, at every breakpoint. Three options at 360px leave about 95px each: enough for "Saturday", not for two words. If an option needs two words, use the list.
  • A .choice-group--row wraps onto more lines when it runs out of room, with 24px between options. Under 576px prefer the vertical list for anything longer than "Free only".
  • The vertical list does not change with width. Descriptions wrap under their label; the radio stays aligned with the first line.
  • Hover tints apply only under (hover: hover); touch never leaves a sticky hover.

Theming

The native radio is tinted with accent-color: var(--colorStatusSuccessBackground3), the forest green shared with checkboxes and the switch, and follows the theme's color-scheme for its unchecked ring. The segmented radio reads --colorNeutralBackground3 for the track, --colorNeutralBackground1 and --shadow4 for the selected pill, and --colorNeutralForeground2 / --colorNeutralForeground1 for the labels.

In the dark theme the track is the lighter umber well and the selected pill is the card surface, so the pill sits darker than the track and the shadow barely shows. The label colour change then carries most of the state, which is why the selected pill also carries an accessible stroke. Neither variant has component tokens; re-skin a track by overriding the alias tokens on a wrapping element.

Accessibility

Role and pattern

Native <input type="radio"> elements with one shared name, which is the APG Radio Group pattern built in. The list sits in a <fieldset> with a <legend>; the segmented radio is a <div role="radiogroup"> labelled by the visible .field__label. Do not build a radio group from buttons; the D13 star rating does, and must manage aria-checked and roving focus by hand (see rating).

Keyboard

KeyAction
Tab / Shift+TabMoves into the group, landing on the checked radio (or the first one when none is checked), and out of the group. The group is one tab stop.
→ / ↓Moves to the next option and checks it, wrapping from the last to the first.
← / ↑Moves to the previous option and checks it, wrapping from the first to the last.
SpaceChecks the focused option if it is not already checked.

Focus

The shared ring (2px --colorStrokeFocus2, 2px offset) appears on :focus-visible. On the list it rings the 18px radio; on the segmented radio, .seg-radio__opt:has(input:focus-visible) moves the ring to the whole pill so it is not hidden under the zero-opacity input.

Labelling

Each option is a <label> wrapping its input, so the visible text is the name and clicking the text checks it. The group is named by its legend or by aria-labelledby pointing at the question ("Which day"); without it a screen reader announces "Saturday, radio button, 1 of 3" with no question. Descriptions inside .check__desc are part of the label. Errors are linked with aria-describedby on the group.

The selected segment is told apart by its white pill and darker label. The pill against the track is a low-contrast surface change, so the selected pill also takes a 1px --colorNeutralStrokeAccessible edge (1.4.11), the same fix D26 made for pressed filter chips.

Motion

None. The selected pill switches instantly; the label colour transitions over --durationFast, which is zeroed under prefers-reduced-motion.

Touch

The whole label is the target: a segmented option is 36px tall and at least 95px wide at 360px; a list row is at least 24px tall with 12px between rows. The 18px radio alone would be too small, which is why the label must wrap the input.

Content

  • The group label is the question, in sentence case, no colon: "Which day", "How far will you drive?". Use a question mark only for a full question.
  • Segmented options are one word, nouns or days: "Saturday", "Sunday", "Either". Never "Yes" and "No" in a segment; a yes/no setting is a switch.
  • List options start with the part that differs: "Up to 30 minutes", "Up to 45 minutes". Put examples in the description, not the label.
  • Order options logically (days in order, distances ascending), not by preference. Put the catch-all ("Either", "Any") last.
  • Error messages say what to do: "Choose the day Piano lesson happens." not "Day is required."

Sources

Extracted from these mocks:

  • pages/dialogs: D7 Add an errand (three-option "Which day"), D18 Edit and Add a commitment (two-option "Day", no default in Add), D28 Add an idea to a day.
  • pages/create-account: the .check row the radio list shares with the checkbox.

The mocks never use a native radio list; the .choice-group examples here are the documented form for when one is needed. The D17 member dialog uses an Age field ("Under 18 counts as a kid") rather than a Parent | Kid choice; if that choice comes back, it is a two-option segmented radio.

Rules added to components.css for this page: an accessible stroke around the selected segment pill, an invalid edge for .seg-radio[aria-invalid="true"], and a real :hover for .check rows to match the data-state twin.
