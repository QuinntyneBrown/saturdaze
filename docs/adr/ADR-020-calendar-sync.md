# ADR-020 — Calendar sync: Google Calendar through an authorization code grant, any other calendar through a subscription link

**Status:** Accepted
**Date:** 2026-10-20
**Category:** identity-and-access, weekend-planning
**Deciders:** Quinntyne Brown
**Implements:** [L2-172](../specs/L2.md#l2-172-connect-a-google-calendar) → [L2-180](../specs/L2.md#l2-180-calendar-data-stays-with-the-family-that-connected-it) (L1-040).
**Related:** [ADR-007](ADR-007-refresh-token-session-lifecycle.md) (token hashing), [ADR-008](ADR-008-per-user-family-scoping-and-auth-fallback.md) (family scoping, anonymous surface), [ADR-010](ADR-010-visual-parity-policy.md) (visual parity), [ADR-016](ADR-016-family-ownership-and-member-sign-in.md) (members), [ADR-019](ADR-019-sign-in-with-google.md) (sign in with Google), [L2-086](../specs/L2.md#l2-086-share-and-export-a-weekend) (calendar export).

## Context

Families already keep their weekends in a calendar. Today the weekend page offers a one-off `.ics` download (L2-086); it goes stale the moment the plan changes, and the planner cannot see the birthday party that is already in the family's calendar unless someone types it in as a commitment. L1-040 asks for an optional, per-account sync that writes the plan into the calendar, follows every change, and reads the weekend's events back as commitments; Google Calendar first, any other calendar second.

ADR-019 chose Google Identity Services ID tokens for sign-in precisely because they need no secret and no call from the API to Google, and it listed the authorization code grant (its option 2) as the path to take "if the product ever reads Google data". Calendar sync is that case: reading and writing a calendar while the person is away needs a refresh token, and a refresh token needs a confidential client. The questions are how the grant is obtained and stored, where the itinerary write runs and how it recovers, how calendar events enter the planner, what serves calendars other than Google, and how all of it is tested without a Google account.

## Decision

1. **Authorization code grant, redirect to the app, exchange in the API.** `POST /api/calendar/google/authorize` (bearer) returns Google's authorization URL with `response_type=code`, `access_type=offline`, `prompt=consent` (so Google always issues a refresh token), the scopes `openid email https://www.googleapis.com/auth/calendar.events` and a `state`. The redirect URI is on the **app origin**, `{Saturdaze:Share:AppOrigin}/family/calendar/google`, an Angular route. The SPA reads `code` and `state` and posts them with its bearer to `POST /api/calendar/google/connect`, which exchanges the code at `https://oauth2.googleapis.com/token` with the client secret. The callback therefore stays an authenticated JSON endpoint: no cookie scheme, no anonymous callback on the API origin, nothing added to L2-008 for it. The `state` is a Data Protection payload of the user id and an expiry 10 minutes out, so it binds the round trip to the person who started it without server-side storage. Sign-in is unchanged: `POST /api/auth/google` and the Google button keep ADR-019's ID-token flow, and the calendar connection is a separate grant that may name a different Google account.
2. **One client, one new secret, off when empty.** The same OAuth client serves both features: `Saturdaze:Google:ClientId` (public) and the new `Saturdaze:Google:ClientSecret`, which comes from the GitHub secret `GOOGLE_CLIENT_SECRET` through `eng/infra/main.bicepparam` and `eng/infra/main.bicep` into the API's app settings, as `SATURDAZE_JWT_SIGNING_KEY` does. When either value is empty the calendar endpoints answer `503 google_calendar_not_configured`, `GET /api/calendar` answers `googleConfigured=false`, and the family page hides the Google row; the subscription link keeps working. This reconciles ADR-019's "no secret" with this feature: sign-in still needs none, and a deployment without the secret simply has no Google calendar sync.
3. **Refresh tokens encrypted with ASP.NET Core Data Protection.** `CalendarConnection.ProtectedRefreshToken` holds the refresh token protected by `IDataProtector` with the purpose `Saturdaze.CalendarSync.GoogleRefreshToken.v1`. The key ring persists to `Saturdaze:Calendar:KeyDirectory` (`/home/data/keys` in Azure, on the App Service's persistent storage, apart from the database) and uses the default key ring when the setting is empty (development, tests). A key ring that is lost makes every grant undecryptable; the connection then reads as `needs_reconnect`, which is the same recovery as a revoked grant. Access tokens are never stored; they are cached in memory for their lifetime minus a minute. Subscription feed tokens are random 32-byte tokens stored only as their SHA-256 hash through `IJwtTokenService`, like share links (L2-086) and refresh tokens (ADR-007).
4. **The itinerary write runs off the request path, from a durable flag.** Every MediatR command that changes the current weekend implements the marker `IChangesItinerary`. `CalendarSyncBehavior` runs after such a command succeeds and asks `CalendarSyncScheduler` to mark every `connected` connection of the caller's family as pending (`SyncRequestedUtc`) and to wake `CalendarSyncService`. That hosted service runs in the API process beside `EmailDispatchService`; it wakes on the signal or every `Saturdaze:Calendar:PollSeconds` (60 by default), and syncs each pending connection whose `NextAttemptUtc` is due by sending `SyncCalendarConnectionCommand`. The handler reconciles rather than replays: it computes the desired events from the family's current weekend, compares a fingerprint per block with `CalendarEventLink` rows, and inserts, updates or deletes only the differences; an event deleted in Google (404/410) is inserted again. Success clears the flag; a transient failure doubles the back-off from 1 minute up to 60 and keeps the flag; `invalid_grant` sets `needs_reconnect` and clears it. Because the pending flag lives in the database, a restart resumes where it stopped; because the write reconciles, retries are idempotent. `Saturdaze.Worker` is not used: it hosts the ingestion schedule and has no request context, and the write must start seconds after the change.
5. **Calendar events join the planner's fixed blocks.** `PlannerInputLoader` asks `ICalendarCommitmentSource` for the weekend's events from every connected account in the family with "plan around my calendar" on, with a 5-second budget; a failure returns nothing. The events become `CalendarCommitment` records in `PlannerInputs.CalendarCommitments`, and `WeekendPlanner.BuildFixedBlocks()` turns them into locked `Commitment` blocks marked `FromCalendar`, after the profile commitments and the carried-over locked blocks, dropping any that would overlap a block already placed. There is no second fixed-block path, and the planner's rule that fixed blocks never overlap holds without a new conflict.
6. **The subscription link is the provider-agnostic path; no second OAuth provider now.** `GET /api/calendar/feed/{token}.ics` serves the family's current weekend as `text/calendar`, reusing the `.ics` writer the export already has, and joins the anonymous capability URLs of L2-008 because calendar applications cannot send a bearer. Apple Calendar, Outlook and Google Calendar all subscribe to a URL, so one endpoint serves every other calendar at no per-provider cost. Microsoft 365 and Apple would each need their own OAuth client, consent screen, token storage and write client for the same outcome in the write direction; they are deferred until a family asks for the read direction there.
7. **Tests stand in for Google at both boundaries.** The Application layer sees only `IGoogleCalendarClient` (authorization URL, code exchange, revoke, list, insert, update, delete), whose failures are `GoogleCalendarGrantRevokedException` and `GoogleCalendarUnavailableException`. API tests replace it with `FakeGoogleCalendarClient`, an in-memory calendar per refresh token with switches for refused codes, missing scope, outages and revoked grants, so every rule in L2-172 → L2-180 runs against the real database and the real background service. `GoogleCalendarClientTests` drive the real client through a fake `HttpMessageHandler`, so the request shapes and Google's error mapping are covered without the network. Playwright answers the calendar endpoints from route stubs and stands in for Google's consent screen by sending the browser straight to `/family/calendar/google?code=…&state=…`, as ADR-019 does for the sign-in button; the subscription link runs against the real API.

## Options Considered

### Option 1: Authorization code grant redirected to the app, exchanged by the API (chosen)
- **Pros:** The callback carries the bearer, so family scoping and the anonymous list are unchanged; the client secret stays in the API; the design-system dialog explains the scopes before Google's screen.
- **Cons:** One more secret to deploy; the redirect URI must be registered in Google Cloud for every app origin.

### Option 2: Redirect to the API origin with ASP.NET Core's OAuth handler
- **Pros:** Framework-provided code exchange.
- **Cons:** An anonymous callback on the API origin, a cookie to carry the user across the round trip and a cross-origin hand-off back to the SPA; the same objections ADR-019 raised against option 3.

### Option 3: Google Identity Services token client (implicit access tokens in the browser)
- **Pros:** No secret.
- **Cons:** No refresh token, so nothing can be written when the person is not on the page; the plan would drift the moment it changes from another device.

### Option 4: Write in the request path
- **Pros:** The calendar is up to date when the response returns.
- **Cons:** Every plan change waits on Google, and an outage fails or slows the family's request, which L2-177 forbids.

### Option 5: A table-backed outbox of individual writes
- **Pros:** Each write is visible as a row.
- **Cons:** Ordering and coalescing problems (a regenerate followed by a swap produces writes for blocks that no longer exist); reconciling against the current plan makes every retry idempotent with one flag per connection.

### Option 6: Encrypt with an AES key from configuration
- **Pros:** No key ring.
- **Cons:** Another secret to rotate by hand; Data Protection already ships with ASP.NET Core and handles key rotation.

## Consequences

- New tables `CalendarFeeds` (migration `AddCalendarFeeds`), `CalendarConnections` (`AddCalendarConnections`) and `CalendarEventLinks` with the connections' sync columns (`AddCalendarSync`), and the column `ItineraryBlocks.FromCalendar` (`AddItineraryBlockFromCalendar`). Apply them with `saturdaze migrate`.
- Infrastructure takes the `Microsoft.AspNetCore.DataProtection` package rather than the ASP.NET Core shared framework, because `Saturdaze.Worker` runs on the plain .NET runtime image. It brings `System.Security.Cryptography.Xml`, whose central pin moves to 10.0.13 (GHSA-r955-8q5j-3h83).
- The subscription link's token is part of a URL that ASP.NET Core logs with every event of a request; `CalendarFeedTokenRedactor`, a Serilog enricher in the API, rewrites it before any sink sees it (L2-177).
- Google Cloud needs a manual change outside the repo: the Calendar API enabled, the `calendar.events` scope on the consent screen, the redirect URI `https://app.saturdaze.ca/family/calendar/google` (and `http://localhost:4200/family/calendar/google` for development) on the web client, and its secret stored as `GOOGLE_CLIENT_SECRET`. `README.md` lists the steps. Until then the Google option is hidden.
- `calendar.events` is a sensitive scope; Google shows an "unverified app" warning to anyone outside the test users until the consent screen passes verification.
- Events already written stay in the person's calendar after a disconnect, because the grant is revoked first and nothing can delete them afterwards. A future requirement could delete them before revoking.
- A calendar event changed after the weekend was planned takes effect on the next generated weekend, as a profile commitment does (L2-011); the feed and the write cover only the current weekend.
- The share link's projection titles calendar blocks "Busy", so a personal event title never reaches an anonymous viewer; the feed leaves them out for the same reason.
- Accepting a family invitation through Google, a Microsoft 365 or Apple provider, more than the current weekend in the feed, and calendar sync for Saturdaze Admin and sample weekends (L1-038) are out of scope.
